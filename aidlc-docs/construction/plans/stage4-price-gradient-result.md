## 1. 3つを1本の線で読む

```
産地の島で安く買う  →  運ぶ  →  向く島で高く売る
   （4-6 仕入れの傾斜）        （4-5 売値の傾斜）
                    ↑ 1品に賭けられる量は 999 で頭打ち（4-7）
```

- **4-5** は既に入っている（commit `2225bd4`）。D1 の効き目を `売れやすさ` → `値段` に替えた
- **4-6** が今回の本体。仕入れ側に逆向きの傾斜を付けて、往復の片道を作る
- **4-7** は、その往復を「同じ1品で無限に回す」に潰させないための天井

## 2. 4-6 産地の島では安く買える

### 実装

`derive.ts` に定数1つと、産地と現在地を突き合わせる関数1つ。

```ts
export const ORIGIN_DISCOUNT = 0.8          // 仮置き。#61 で測り直す
purchasePrice(itemId, at?)                  // at を渡すと、その島を産地とする品だけ 0.7 × 0.8
```

### ⚠ 例外を1行も書いていない — 担保はデータの形にある

**産地を持つのは tier1 の43品だけ**（実測。tier2 以上は **0品**）。
加工品79品はすべて産地が `なし`（旬を持たないため。#22）。

したがって「tier を見る」「加工品を除く」という条件を**どこにも書かずに**、
**割引は素材にしか当たらない**。実測で 4島合計43件の割引すべてが tier1。

これが「**加工が転売に食われない**」の担保そのもので、
`ItemRegistry.test.ts` の2本（「割引は素材にしか当たらない」「出来上がりは割引を受けない」）が
**データの形が崩れたら落ちる**ようにしてある。

### 島ごとの実測

| 島 | 産地の品 | うち その島に向く品 | 平均買値 素 → 産地 |
|---|---|---|---|
| ハルヴェラ | 11品 | **8品** | 28 → 22 |
| リナツィア | 9品 | 2品 | 44 → 35 |
| ノアキータ | 12品 | 1品 | 28 → 23 |
| ミフユリア | 11品 | 2品 | 37 → 29 |

例: かに（ミフユリア産）売144 ／ 買101 → **ミフユリアでは81**。

⚠ **「うち その島に向く品」は往復にならない。**その島で安く買えて、その島で高く売れるので、
運ぶ理由が出ない。**ハルヴェラは11品中8品がこれ**で、傾斜が最も効かない島になっている。
これは需要表（`向く土地`）と産地の割り当てが噛み合っていない、という**データ側の話**なので、
値をいじって直すものではない。→ **#61 の測り直しに送る**（本メモ §6-1）。

## 3. 4-7 在庫の上限 999

### 決めたこと — **買えない**（黙って消さない）

| どこ | 上限に当たるとどうなるか |
|---|---|
| **仕入れ** | 空きが5個に満たない行は**押せない**。ボタンの位置に「上限999」と出る。**払ってから消える、が起きない** |
| **加工** | 出来上がりは `add` が丸める。上限に達したら `GameScene` がログに「在庫上限 999 に達した。これ以上は増えない」と出す |
| **持ち物一覧** | 数の横に「（上限）」。仕入れ画面まで行かないと分からない、にしない |

旧実装は `MAX_QUANTITY = 99999` を `Math.min` で丸めるだけで、**超えたぶんは黙って消えていた**
（代金は払ったまま）。`Inventory.ts` の注記が「下げるときは溢れたぶんの扱いを先に決めること」と
警告していた箇所で、今回それを決めた。

### API を1つ増やした

- `add()` が**実際に入った数を返す**（要求より少なければ溢れた）
- `spaceFor(itemId)` / `isFull(itemId)` で**買う前に**空きを訊ける

⚠ **加工側は「出来上がってから溢れる」形のまま。**塞ぐには `CraftingSystem.maxCraftTimes` に
在庫上限を足すのが筋だが、今回の依頼の触ってよい範囲に `CraftingSystem.ts` が無い。→ §6-2

## 4. 受入条件3 — 符号の確認（1回だけ）

**「材料を買って作る」が「買ってそのまま売る」より儲かる、が全レシピで成り立つこと。**

```
測った組: (割引なし ＋ 4島) × 72レシピ = 360本
結果    : 360 / 360 で成立
最小マージン: salted_lemon_water +11.00（どの島でも同じ）
```

### なぜ割引で崩れないか（測る前から分かること）

レシピの出力は必ず tier2 以上 ＝ 産地 `なし` なので、**転売側の買値は割引を受けない**。
一方、材料側は産地の島で安くなる。つまり割引は**「作る」の側だけを押し上げる**。

```
作る利益 − 転売利益 ＝ 加工利益 × 買値率 ＋ (割り引かれた材料費ぶん)   ≧ 加工利益 × 買値率 > 0
```

この検査は `ItemRegistry.test.ts` に**4島ぶんへ広げて常設**した（以前は割引なしの72本だけ）。

## 6. 残る疑問（main へ）

1. **ハルヴェラは産地の品11品中8品が「その島に向く品」で、傾斜が往復にならない。**
   安く買える島と高く売れる島が同じなので、運ぶ理由が出ない（リナツィア2／ノアキータ1／ミフユリア2）。
   直すのは値ではなく**産地と `向く土地` の割り当て**なので、#61 の測り直しに含めるか判断が要る

2. **加工の出来上がりは「作ってから溢れる」。**`CraftingSystem.maxCraftTimes` に在庫上限を足せば
   「作れない」まで持っていけるが、`CraftingSystem.ts` は今回の触ってよい範囲に無い。
   いまはログで知らせるだけ。**issue 化の要否は main の判断**

3. **依頼文の「同じ島の中では買値が全品同じ率」と、4-6 の割引は字面が食い違う。**
   実装では同じ島に率が**2つ**ある（素の 0.7 と、産地の 0.56）。
   守るべき中身 —— `作る利益 − 転売利益 > 0` —— は 360/360 で成立し、
   §4 のとおり**割引では崩れようがない**ので、そちらを守った。
   「率は島ごとに1本」と読み替えてよいか、確認が要る

4. **実機での目視確認をしていない**（#47）。「この島の産」の印・「上限999」の出方・
   持ち物一覧と仕入れ画面で買値が一致することは、**テストではなくブラウザでしか見えない**
