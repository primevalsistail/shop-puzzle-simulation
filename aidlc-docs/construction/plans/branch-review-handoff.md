### 0-1. どんなゲームか

- 舞台は「気候の違う四つの島と、それを結ぶ海」でできた世界（魔法・戦闘なし）。
- プレイヤーは**店舟**（船が接岸すると船倉がそのまま売り場になる）の店主。
- **四島を10日ごとに巡る**。島ごとに気候が違い、採れるものが違う（ハルヴェラ=温暖／リナツィア=暑い／ノアキータ=実りが絶えない／ミフユリア=雪が絶えない）。
- 素材を**仕入れ**、**加工**して商品を作り、**船倉の升目（グリッド）に配置**して売る。
  **隣り合わせに置いた品どうしで効果が変わる**のがゲームの中心（パズル要素）。
- 実装は TypeScript + Phaser 3（2Dブラウザゲーム）、テストは Vitest、ビルドは Vite。
- 現在の到達点は「13品でひと通り遊べる試作」。今回のブランチは**その先の本体設計**にあたる。

### 0-2. 「軸」とアイテムの5属性

アイテムを分類する属性を、この設計では**軸**と呼ぶ。手書きするのは4本、1本は導出。

| 軸 | 意味 | 値 |
|---|---|---|
| 主種類 | その品を人がどう扱うものか | `食料` `飲みもの` `衣類` `道具` |
| 産地 | どの島で採れるか | 4島名 ＋ `なし`（旬を持たない品。加工品はほぼ全部これ） |
| 贅沢さ | なぜ買うか（価格とは別問題） | `日用` < `上等` < `贅沢`（**順序あり**） |
| 向く土地 | どんな土地で役に立つか | `寒い土地` `暑い土地` `温暖な土地` `実りの土地` `どこでも` |
| **tier** | **加工の深さ（導出値・手書きしない）** | `tier = 1 + max(材料のtier)`、レシピ無しは 1。実データでは 1〜4 |

**「向く土地」と「産地」は別物**（どこで採れるか／どこで役に立つか）。
品は**島の名前を知らない**。`islands.ts` の需要表4行だけが「向く土地 ↔ 島」を結ぶ。

### 0-4. 規則の記号（R / D / U）と「甲・乙」

`src/taxonomy/rules.ts` にデータとして置かれている規則。

| 記号 | 種類 | 内容 |
|---|---|---|
| R1〜R6 | **取り合わせ（隣接）層1** | R1 食べもの×飲みもの→売れやすさ1.2 ／ R2 上等以上どうし→値段1.15 ／ R3 日用どうし→売れやすさ1.1 ／ R4 贅沢×日用→値段0.85 ／ **R5 同産地どうし→`店全体`の集客1.1** ／ R6 tier3以上×tier1→売れやすさ1.15 |

**甲（こう）・乙（おつ）** は隣接規則の2つの項。**甲乙は順不同で照合するが、効果は当たった側（甲）にだけ乗る。**

### 0-5. S − D 方式（加工の難易度）

- **S = 手際**（主人公のスキル値。初期10・上限30）／ **D = 難易度**（`tier × 5` で導出、手書きしない）
- 着手条件: `D ≤ S + 8` ／ 所要時間: `基準時間 × clamp(2^((D−S)/5), 0.25, 4.0)`
- 狙いは「作れない／背伸び／適正／量産」の4段階を作ること。
  **設計者自身が「指数式だけなら一律高速化と代数的に同じで、差を作っているのは clamp のほう」と明記している**（第9章⑨の論点）。

## 4. 設計上の変更

### 4-1. 責務の移動

- **時間の停止権が `CraftingSystem` から消えた。** 旧: `CraftingSystem` が `TimeManager.pause()` を呼び時計を支配 → 新: `TimeManager.skipMinutes()` に「時間を進めるが客は来ない」を集約し、`CraftingSystem` は消費者になった
- **「客が来るか」の判定が `GameScene` に露出した。** `GameService.onMinutePassed(rng, isOpen)` は呼び出し側から `isOpen` を注入される形。ドメイン判断がシーン層を経由する
- **「どこで並ぶか」が規則データではなく評価器の実装に置かれた。** `stockedByIslandMerchant`（`src/taxonomy/evaluate.ts:277`）が U3/U4 相当をハードコード。条件言語に「軸どうしの比較（`産地 == 現在地`）」が無いため、と作者は明記（issue #31）

### 4-2. 新しい抽象化

1. **条件言語（DSL）** — `Predicate` / `Condition`（かつ・または・でない）。**順序演算子を `tier` と `贅沢さ` にだけ型で許す**設計（union type で分岐）
2. **`EffectScope: 'その品' | '店全体'`** — 店全体スコープは既存 `AdjacencyEngine` に無い新機構
3. **導出値（INV-3）** — `tier`・価格・難易度を `ItemDef` に置かず関数で出す。テストで「型にフィールドが存在しないこと」を検査
4. **`SuitedLand`（向く土地）** — 品は島名を知らず、`islands.ts` の需要表4行だけが結びつける。島の気候を変えても品は無傷

## 7. SE判断が必要な論点

### SE-1. `src/taxonomy` を本体に接続するか、するならどこまでか【最重要・未決】

計画書の Question 1 が空欄のまま。選択肢は A) 現在地をハルヴェラ固定にして接続（推奨と記載）／B) 巡航まで実装／C) 島まわりを外して接続。
**接続しない期間が長いほど、未使用の 2,500行が腐る。** 接続時に既存テスト5本が壊れることは予告済み。
→ **判断: 接続の可否・範囲・優先順位。**

### SE-2. `店全体` スコープと `AdjacencyEngine` の関係

`evaluate()` は隣接判定を内包しており、既存 `AdjacencyEngine` と機能が重複する。計画書は「役目がほぼ無くなる。薄い変換だけ残すか、消す」としている。
→ **判断: `AdjacencyEngine` を廃止するか、`evaluate` のアダプタとして残すか。**

### SE-3. 「場所の条件」を条件言語に入れるか（issue #31）

`産地 == 現在地` という**軸どうしの比較**が DSL に無いため、U3/U4 と D2 と R5 の一部が**評価器のハードコード**になっている。作者は「規則データが嘘をつくよりは持たないほうがよい」として U4 を削除した。
→ **判断: DSL に軸参照（`{ axis: '産地', op: '==', ref: '現在地' }` 等）を足すか、評価器持ちのままにするか。**現状は規則データ駆動という設計目標が半分しか達成されていない。

### SE-4. 効き目の上限を設けるか（R-10）

「上限を設けるのはバランス調整であり、数値調整はスコープ外」という理由で意図的に無制限。しかし `店全体` の集客は隣接ペア数に比例して積む。
→ **判断: 構造的な上限（設計）か、係数調整（バランス）か、どちらの問題として扱うか。**

### SE-5. `CraftingSystem` の抜け殻 API を今整理するか（R-5）

`update`/`cancelCraft`/`getProgress`/`isActive`/`getActiveJob` と `activeJob` フィールドが実質デッド。UI 側（`CraftMenu`・`GameScene`）が到達不能なコードを保持している。
→ **判断: 今このブランチで削除するか、#30 の接続作業とまとめるか。**

### SE-6. 手際（skill）をゲーム状態としてどこに置くか

`craft.ts` は `skill` を引数で受けるのみ。プレイヤー状態としての置き場所（`GameProgress`？新規 `PlayerState`？）とセーブデータへの反映が未設計。
→ **判断: 責務の配置とセーブ互換性。**

### SE-7. `isOpen` の注入経路（R-4）

現在は `GameScene` が `timeManager.isOpen()` を `GameService` に渡す。デフォルト値 `true` は fail-open。
→ **判断: `GameService` に `TimeManager` を注入する／`TIME_MINUTE_PASSED` のペイロードに `phase` を含める／デフォルト値を削除して必須引数にする、のいずれか。**

### ⑪ 時間モデルの境界値と非対称なイベント発火

- **ファイル**: `src/components/core/TimeManager.ts:82-124`
- **箇所**: `minutesUntilEndOfDay()` / `skipMinutes()` / `tick()` / `advanceMinute()`
- **なぜ**: (a) `tick()` は `TIME_PHASE_CHANGED` を出すが `skipMinutes()` は出さない（**非対称**）。(b) `skipMinutes` は複数日をまたいでも `TIME_DAY_CHANGED` を1回しか出さない。(c) `advanceMinute` は 24:00 で `hour = 6` に飛ばすので、**通常プレイで hour が 0〜5 になることはない**が `setTime` では設定可能（`phaseOf` は `睡眠` を返す）。(d) `skipMinutes` は1分ずつループ（最大480回）
