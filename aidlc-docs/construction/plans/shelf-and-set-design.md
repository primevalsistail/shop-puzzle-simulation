# 棚の刻みと、組み合わせボーナスの拡張性

**作成**: 2026-09-11 ／ main
**きっかけ**: PO から2点 — (1)13段は多い。5〜10段で長方形を崩さず同比率に刻めるか
(2)組み合わせボーナスは「同じ棚に並べること」も含む。商品によって変えることもありうるので拡張性を検討

---

## 1. 棚の刻み

### 前提（実測）

- 画面に入るのは **14×10 = 140升**（`CELL_SIZE = 58`、グリッド領域 x228〜1090 / y8〜609）
- ⚠ **`CELL_SIZE` を小さくすればもっと入る。**要件 FR-UI-02-6 は「セルサイズを動的計算」と書いているが、
  **実装は 58px 固定。**升目を増やすより先にここを決める必要がある
- 開始は **6×5 = 30升**、縦横比 **1.20**

### ⚠ 最終盤面は **13×10（130升）**を勧める

**14×10 は縦横比 1.40** で、6×5（1.20）からはっきり横長に寄る。
**13×10 は 1.30** で収まる。1段ぶん（10升）を捨てて比率を保つ形。

### 段数ごとの最良の刻み

「面積が等比に近い」「縦横比が 6:5 から離れない」で探索した結果。

| 段数 | 1段あたり | 刻み | 縦横比の振れ |
|---|---|---|---|
| **4段** | **×1.38** | 6×5 → 7×6 → 8×7 → 10×8 → **11×10(110)** | 1.20〜1.10 |
| **5段**【推奨】 | **×1.34** | 6×5 → 7×6 → 8×7 → 9×8 → 11×9 → **13×10(130)** | 1.20〜1.30 |
| 6段 | ×1.28 | 6×5 → 6×6 → 8×6 → 9×7 → 10×8 → 10×10 → 13×10 | 1.00〜1.33 |
| 7段 | ×1.22 | 6×5 → 7×5 → 7×6 → 7×7 → 9×7 → 10×8 → 11×9 → 12×10 | 1.00〜1.40 |
| 8段 | ×1.19 | 6×5 → 7×5 → 7×6 → 8×6 → 8×7 → 8×8 → 10×8 → 11×9 → 12×10 | 1.00〜1.40 |

**推奨は5段。**理由:

- **1段 ×1.34 は「広くなった」と分かる大きさ。**7段以降は ×1.22 以下に落ち、正方形（比率1.00）や
  横長（1.40）を経由するので**形が安定しない**
- 最初の3段（7×6・8×7・9×8）は**1辺ずつ交互**で素直。後半2段で大きく飛ばして13×10に着く
- 段が少ないほど**1段の費用を高くできる**（PO の「だんだん高くしたい」と噛み合う）

⚠ **13段案（1辺ずつ全部刻む）を捨てる理由**: 1段が ×1.10〜1.20 にしかならず、
**買っても変化が分からない。**サブの実測でも「7段のうち1段で伸びの76%」という偏りが出ていた。

## 2. 組み合わせボーナスの拡張性

### いまあるもの

| 層 | 中身 | 隣接 |
|---|---|---|
| 層1 | `PAIR_RULES` R1〜R6。**軸の条件**で書く（食べもの×飲みもの、など） | 要る |
| 層1 | `SAME_ORIGIN_RULE` R5。同じ島の産 → **店全体**に集客 | 要る |
| 層2 | `SIGNATURE_PAIRS` 名物コンビ。**品IDを名指し**。**既定は空** | 要る |

**足りないのは「同じ棚に並んでいればよい（隣接を要らない）」という条件。**

### 提案 — 3つを1つの形にまとめる

```ts
export interface SetRule {
  readonly id: string
  readonly description: string
  /** 揃える対象。**品IDの列挙**でも **軸の条件**でも書ける */
  readonly members: readonly ItemId[] | Condition
  /** 何種類そろえば成立するか。省略すると members 全部 */
  readonly count?: number
  /** true=隣り合っていること／false=**同じ棚にあればよい** */
  readonly adjacent: boolean
  /** 効き目。scope で「揃えた品だけ」か「店全体」かを選ぶ */
  readonly effect: Effect
}
```

**拡張性はこの4点で確保する:**

1. **`members` が2通り書ける** — 「りんごと蜂蜜」（品ID）も「贅沢な飲みもの」（軸の条件）も同じ形。
   **品を足しても、軸で書いたセットは自動で拾う**
2. **`adjacent` の真偽だけで層1・層2・同棚を統一** — 別々の仕組みを作らない
3. **`count` で部分成立** — 「5種のうち3種そろえば」が書ける
4. **`effect.scope`** — 「揃えた品だけ値が上がる」も「店全体に人が寄る」も既存の仕組みで書ける

### ⚠ 守るべき2つの決まり（Cycle 4 の不変条件）

- **INV-5: 品を1つ足すときに書くのは品の定義1件だけ。**
  → **セットの所属を品側に書かない。**必ずセット側に列挙する。
  「商品によって変える」は**セット定義を足す**ことで行う
- **INV-4: 層2を全部消しても層1だけで成立する。**
  → **セットの既定は空**にできること

### ⚠ 技術的に1つ新しいものが要る

「同じ棚にあればよい」は **盤面の集合に対する条件**で、
いまの条件言語（`Condition`）は**品1つに対する条件**しか書けない。

ただし **評価器が集合を見るのは既にやっている**（R5「同じ島の産」・D2「よその島の産」）。
**分界どおり「集合の判定は評価器、条件は規則データ」**に収まるので、
**条件言語の拡張（#31）は要らない。**

⚠ ただし `stockedByIslandMerchant` が `r.id === 'U1'` と**IDで名指し**している歪み（#31 の申し送り）は
繰り返さないこと。**セットは最初からデータ駆動にする。**
