## 0-2. ★セッションの分離（Q4）

**このセッションは「起こす」側に徹する。「評価する」側は別セッションが行う。**

| | 起こすセッション（**いまここ**） | 評価するセッション（**別セッション**） |
|---|---|---|
| やること | Step 1〜9・11 — 島の産物／型／20品／レシピ／導出／規則／評価器／**INV 自動テスト** | **Step 10** — §7「確かめること」5件の**計測コードを書き、走らせ、判定する** ＋ **Step 12** — Phase 4 の可否 |
| 渡すもの | `src/taxonomy/` 一式 ＋ **自己完結した依頼書** | 判定結果 |

**なぜ分けるか**: 計測コードを書く者と判定する者が同一だと、**自分のデータを褒める計測**を
無意識に書きうる。Step 10 の5件は Phase 2 §7 が項目を挙げただけで**合格ラインが未定義**なので、
起こした本人が基準を後付けできてしまう。

**INV-1〜6 は起こす側に残す。** Phase 0 が判定方法まで外部で先に定義しており（「ダンプ→追加→再ダンプ、
差分が空」など）、後付けの余地がないため。**基準が未定義なものだけを評価セッションへ移す。**

**手法の先例**: Cycle 3 の [worldbuilding/prompts/](../../inception/worldbuilding/prompts)。
依頼書は**そのファイルだけで判断できるように**書く（他の資料を読ませない）。

### この計画で決めないこと
- **利幅の数値バランス調整**（Cycle 4 のスコープ外。item-system.md §5「要調整・別件」）
- **客のモデル**（Cycle 5）。条件言語の器だけ用意する
- **ゲーム本体への接続**（GameScene / CustomerSimulator の差し替え）。Phase 4 の後に別途

### 実装の置き場所
```
src/taxonomy/                     ← 新設。既存に触れない
  axes.ts          5軸の型と値、ItemDef（新）
  islands.ts       四島の気候、島の需要表4行
  items.ts         実アイテム20品
  recipes.ts       レシピ
  derive.ts        導出（tier / 売値の積み上げ）
  rules.ts         条件言語の型 ＋ 規則データ（層1 / 層2 / 島の需要 / 入荷解禁）
  evaluate.ts      規則評価器（効き目の集約。範囲 その品 / 店全体）
  *.test.ts        各モジュールのテスト
  invariants.test.ts   INV-1 / 3 / 4 / 5 / 6 の自動判定
  checks.test.ts       Phase 2 §7「確かめること」5件の計測
```

### 命名の方針（着手前に決めておく）
- **フィールド名は英語**（`mainKind` `origin` `luxury` `suitedLand`）— 既存コードの流儀に合わせる
- **軸の値は日本語リテラル**（`'食料'` `'贅沢'` `'寒い土地'`）— PR-1「説明が要る名前は負け」を守るには、
  設計文書の語と**コードの語が字面で一致している**必要がある。英訳を挟むと `luxury` と `贅沢さ` の
  対応表を誰かが覚えることになり、それ自体が PR-1 の負けである
