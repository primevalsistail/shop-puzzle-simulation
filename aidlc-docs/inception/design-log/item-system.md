## 1. 決めようとしていること

アイテムの分類体系。ユーザー要望は以下。

- アイテムは **「種類」と「tier」** を持つ
- 種類は **5〜10** 程度
- tier は **最大10** 程度
- **拡張しやすいこと**（アイテムを足し続けても壊れない）

背景として、「主人公が買う → 何かを作る → 売る」というオーソドックスなクラフトループを
正面から取り入れたい、という意図がある。

## 3. 却下した案と理由 ★重要

| 却下案 | 却下理由 | 得られた原則 |
|---|---|---|
| **糧・装・具・知・奇**（抽象漢字5分類） | 初見で意味が取れない | **説明が要る名前は負け** |
| **書物**（紙製品カテゴリ） | 他は動詞（食べる・飲む・着る・使う）で切っているのに、これだけ**素材**で切っていた。だから狭かった | **1つの分類の中で切る軸を混ぜない** |
| **`原料` という主種類**（2026-09-06） | 「用途を持たないもの」は**用途の不在**で切っており、他の値（用途）と切り方が違う。**「書物」と同型** | 同上。木材・布は用途側へ寄せた |
| **面「保存」**（生鮮／常温）（2026-09-06） | Phase 1 で取り下げた「傷むか」の入れ直し。時間劣化の機構が無いので `生鮮` の**定義文が書けない** | **効き目は書けても、値の定義が書けないものは軸にならない** |
| **面「客層」**（子供向け等）（2026-09-06） | 向きが逆。品側に置くと**客を1種増やすたびに既存の全品を書き換える**。`子供向け` は「子供という客が居る」ことに依存する外部依存の値 | **「誰に売れやすいか」は品の事実ではなく意味づけ。規則側に置く** |
| **面「消耗」**（使い切る／残る）（2026-09-06） | 根拠が「**同じ客が繰り返し買う**」だったが、**この世界の客には同一性が無い**（個人を作らない）。根拠の事象が存在しなかった | **軸を足す前に、その軸が前提にしている事象がこの世界にあるか確かめる** |
| **素材 → 中間品 → 製品** | 生産グラフ上の**相対位置**。サンドイッチのレシピを足すとパンが「製品」→「中間品」に変わる。つまり**アイテムを足すと既存アイテムの分類が変わる** | **分類は絶対値でなければ拡張できない** |
| **tier = 価格帯**（等比ラダー） | 価格は tier の**結果**であって定義ではない。tier3 を材料にするなら出力は tier4 であるべき | **tier は加工の深さ** |
| **UI幅から分類数を6〜8に絞る** | データモデルの分類数と、フィルタUIの選択肢数は**別物**。多い分類をUIに載せる方法は普通にある（親でまとめる／検索／ピン留め） | **UI制約はフィルタ設計への制約であって、分類設計への制約ではない** |
| **主種類 =「客がその品を買う理由」** | 同じ食品でも子供が買うものと大人が買うものがある。購買傾向は品ごとの性質 | **「誰が買うか」は主種類では表現できない** |
| **アイテムを1000個挙げてから分類** | 挙げながら語彙をその場で発明することになり収束しない。また1000品は画面に並ぶ上限（最大60品）を大きく超える | **列挙するなら、アイテムより先に規則を列挙する** |
| **響き**（隣接シナジーの呼称） | 字は読めるが、棚の上で何が起きるのかの像が結ばない。世界観案のプレイヤーレビューで、同型の「共鳴」が同じ理由で下位評価だった | **用語は、それが指す操作と字面で繋がっていること** |

### 根本原因

**1つの軸に複数の問いを兼任させていた。**

「種類」に以下すべてを答えさせようとしていた:

- どの棚に置くか
- 誰が買うか
- 何から作れるか
- 何と取り合わせるか
- いつ解禁されるか

この5つはアイテム空間を**別々の線で切る**ので、1分類で全部やると必ず破綻する。
矛盾にぶつかるたびに「軸が1本足りない」という信号が出ていた。

### 取り合わせを2層で書く理由（**2026-09-13 に §6 から移設**）

> ⚠ **下のコード例の値は失効している**（`生鮮` は面「保存」ごと却下、`要素` は面に分割済み、`placeable` は廃止）。
> **有効なのは「2層で書く」という構造のほう。**現行の確定形は
> [Phase 2 §4・§5](../application-design/cycle4-phase2-axes.md) を参照。

現行は**アイテムID同士の直書き**（`apple: { adjacentItemId: 'milk' }`）。
100品に増えると組み合わせが数百行になり、**1品足すたびに既存全品との関係を見直すことになる**。
これが「拡張しづらい」の本丸。

```ts
// 層1: 条件規則（広く浅く・数十行で全品カバー）
{ when: ['食品', '飲料'],     type: 'sales_rate', mult: 1.15 }
{ when: ['贅沢', '贅沢'],     type: 'price_up',   mult: 1.20 }
{ when: ['生鮮', '生鮮'],     type: 'sales_rate', mult: 0.9  }  // 負の取り合わせも書ける

// 層2: 個別規則（狭く深く・名物コンビだけ手で作る）
パン × ワイン → price_up 1.3
```

→ 新しい品は要素を付けた瞬間に既存全品と正しい取り合わせになる。**追加コストが定数になる。**

## 5. なぜ右往左往したか（プロセスの反省）

| 原因 | 内容 |
|---|---|
| **要件を決めずに解に飛んだ** | 「この体系が満たすべき条件」を書かないまま分類案を作ったので、新しい制約が出るたびに前提が変わった |
| **決定順を無視した** | tier の定義が決まれば主種類が背負うべきものは自動的に決まる。逆順にやったので後から前を壊した |
| **毎回"完成品"を出した** | 完成した設計は全体で否決される。次の1決定だけ出すべきだった |
| **実物なしで分類を評価した** | 中身が無い箱を設計していたので、空箱・過疎箱が事後にしか発覚しなかった |

ただし**円環ではなく螺旋**。反転のたびに軸が1本ずつ確定しており、
構造（§2）は固まっている。残っているのは各軸に入れる語彙（§4）だけ。
