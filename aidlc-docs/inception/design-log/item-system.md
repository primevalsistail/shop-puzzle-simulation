## 1. 決めようとしていること

アイテムの分類体系。ユーザー要望は以下。

- アイテムは **「種類」と「tier」** を持つ
- 種類は **5〜10** 程度
- tier は **最大10** 程度
- **拡張しやすいこと**（アイテムを足し続けても壊れない）

背景として、「主人公が買う → 何かを作る → 売る」というオーソドックスなクラフトループを
正面から取り入れたい、という意図がある。

## 2. 確定事項

| # | 決定 | 根拠 |
|---|---|---|
| 1 | 分類は**単一軸ではなく複数軸**に分ける | 1軸に複数の問いを兼任させると必ず矛盾する（§3参照） |
| 2 | **tier = 加工の深さ**。`tier = 1 + max(材料のtier)`、レシピ無しは 1 | 絶対値なので、レシピを足しても既存品の tier が変わらない |
| 3 | tier は **`ALL_RECIPES` から自動導出**。手で書かない | 導出できるものを手書きすると不整合が生まれる |
| 4 | **「何から作れるか」は属性として持たない**（レシピから導出） | 同上 |
| 5 | ~~**客の好みは品ごとの性質**~~ → **客の好みは規則側に置く**（#17 で改訂）。主種類の役目ではない点は変わらない | 「主種類では表現できない」は正しかったが、置き先を品側と読んでいたのが誤り。2026-09-06 |
| 6 | **主種類に残るのは「これは何であるか」だけ** | 棚の整理・表示・数え上げ用。設計の中心ではない |
| 7 | **取り合わせの条件は tier / 主種類 / 要素 のどれでも参照できる**一般形 | 条件を1つの軸に縛る理由がない |
| 8 | **同じ条件言語を 取り合わせ・客の好み・入荷解禁 で共有**する | 規則ごとに別記法を作ると保守できない |
| 9 | アイテムは**事実だけ**を持ち、意味づけは**規則側**に置く | 品を足しても規則を書き直さずに済む |
| 10 | 隣接シナジーの呼称は **「取り合わせ」** | 設定用語はこれ1つだけに絞る（世界観側の決定）。2026-08-29 に「響き」から変更（§3参照） |
| 11 | 要素は**面（facet）に分ける**。平らなタグ袋にしない | 保存性と客層は別の問い。混ぜると INV-2b 違反（「書物」と同型）。2026-09-06 |
| 12 | **産地**を面として持つ。値に**「なし」を含む** | 島の個性はコントラストで立つ。産地なしの品が詰みを緩める。2026-09-06 |
| 13 | **placeable は持たない。全品売れる** | 全品が「今売るか、材料にするか」の選択になる。2026-09-06 |
| 14 | 売値は**積み上げ式**（tier1 のみ手書き、tier2以上は `Σ材料の売値 × 加工倍率`） | tier は和ではないため、tier だけから決めると高い材料を多数使う品で赤字になる（INV-6）。2026-09-06 |
| 15 | 中間品は**その品を100個売ると買えるようになる**（ただし**買う方が高い**） | 深い tier の下ごしらえの連鎖を緩める。既存の入荷解禁規則の適用範囲を広げるだけで、軸は増えない。2026-09-06 |
| 16 | **軸は5本。**主種類 ／ tier ／ 産地 ／ 贅沢さ ／ 向く土地（N=2） | Phase 2 で規則を先に列挙して逆算した結果。→ [Phase 2](../application-design/cycle4-phase2-axes.md)。2026-09-06 |
| 17 | **「誰に売れやすいか」は品側に持たない。規則側に置く** | 品側に置くと客を1種増やすたびに既存の全品を書き換える。§6 の ID 直書きと同じ壊れ方。2026-09-06 |
| 18 | **島は品側に持ってよい**（`向く土地`）。ただし**品は島の名前を知らず**、4行の需要表が結ぶ | 島は world.md §1 で四島に確定していて増減しないため、#17 の壊れ方が起きない。2026-09-06 |
| 19 | **効き目は 種類3（売れやすさ・値段・集客）× 範囲2（その品・店全体）** | 「店全体のボーナス」を同じ書式で書けるようにする。`店全体` は新機構。2026-09-06 |
| 20 | **客のモデルは Cycle 4 で定義しない**（→ Cycle 5「客と需要」） | 来訪モデルはどこにも定義がなく、コードに客の実体も類型も無い。Cycle 4 はアイテム体系に閉じる。2026-09-06 |
| 21 | **産地は「品に割り当てる」のではなく「島から品を起こす」** | 割り当て向きだと毎回「この品はどの島か」の選択が発生し、規律を作っても恣意性が〈島の選択〉から〈品への修飾語〉へ移るだけだった。向きを変えると**産地は選択ではなく出自**になる。→ [island-goods.md §2](../worldbuilding/island-goods.md)。2026-09-06 |
| 22 | **産地 `なし` ＝ 海のもの** | world.md §1 の「四島とそれを結ぶ穏やかな海」から導出。海はどの島のものでもない。U4・詰み回避・島の個性のコントラストを設定を足さずに満たす。2026-09-06 |
| 23 | **気候は「何が育つか」しか決めない** | 四島の気候はいずれも育つものの気候。**かたちになったものはどの島も産さない**ので、着るもの・使うものは tier2 以上に来る。2026-09-06 |
| 24 | **効き目の合成は加算** `1 + Σ(mᵢ − 1)`。上限を設けない | 乗算だと積み上がりが暴走し、上限を置くとそれ自体がバランス調整の数値になる（Cycle 4 のスコープ外）。2026-09-06 |
| 25 | **⚠ 条件言語に「軸どうしの比較」が無い**（`産地 == 現在地` が書けない） | **Phase 3 で見つかった穴。**U3（島の商人は自島産を並べる）／ D2（よその島の産）／ R5（同じ島の産を並べる）の**3規則がこれを要求**しており、いまは評価器が個別に持っている。条件言語に足すかは Phase 4 以降の判断。2026-09-06 |

## 3. 却下した案と理由 ★重要

| 却下案 | 却下理由 | 得られた原則 |
|---|---|---|
| **糧・装・具・知・奇**（抽象漢字5分類） | 初見で意味が取れない | **説明が要る名前は負け** |
| **書物**（紙製品カテゴリ） | 他は動詞（食べる・飲む・着る・使う）で切っているのに、これだけ**素材**で切っていた。だから狭かった | **1つの分類の中で切る軸を混ぜない** |
| **`原料` という主種類**（2026-09-06） | 「用途を持たないもの」は**用途の不在**で切っており、他の値（用途）と切り方が違う。**「書物」と同型** | 同上。木材・布は用途側へ寄せた |
| **面「保存」**（生鮮／常温）（2026-09-06） | Phase 1 で取り下げた「傷むか」の入れ直し。時間劣化の機構が無いので `生鮮` の**定義文が書けない** | **効き目は書けても、値の定義が書けないものは軸にならない** |
| **面「客層」**（子供向け等）（2026-09-06） | 向きが逆。品側に置くと**客を1種増やすたびに既存の全品を書き換える**。`子供向け` は「子供という客が居る」ことに依存する外部依存の値 | **「誰に売れやすいか」は品の事実ではなく意味づけ。規則側に置く** |
| **面「消耗」**（使い切る／残る）（2026-09-06） | 根拠が「**同じ客が繰り返し買う**」だったが、**この世界の客には同一性が無い**（個人を作らない）。根拠の事象が存在しなかった | **軸を足す前に、その軸が前提にしている事象がこの世界にあるか確かめる** |
| **素材 → 中間品 → 製品** | 生産グラフ上の**相対位置**。サンドイッチのレシピを足すとパンが「製品」→「中間品」に変わる。つまり**アイテムを足すと既存アイテムの分類が変わる** | **分類は絶対値でなければ拡張できない** |
| **tier = 価格帯**（等比ラダー） | 価格は tier の**結果**であって定義ではない。tier3 を材料にするなら出力は tier4 であるべき | **tier は加工の深さ** |
| **UI幅から分類数を6〜8に絞る** | データモデルの分類数と、フィルタUIの選択肢数は**別物**。多い分類をUIに載せる方法は普通にある（親でまとめる／検索／ピン留め） | **UI制約はフィルタ設計への制約であって、分類設計への制約ではない** |
| **主種類 =「客がその品を買う理由」** | 同じ食品でも子供が買うものと大人が買うものがある。購買傾向は品ごとの性質 | **「誰が買うか」は主種類では表現できない** |
| **アイテムを1000個挙げてから分類** | 挙げながら語彙をその場で発明することになり収束しない。また1000品は画面に並ぶ上限（最大60品）を大きく超える | **列挙するなら、アイテムより先に規則を列挙する** |
| **響き**（隣接シナジーの呼称） | 字は読めるが、棚の上で何が起きるのかの像が結ばない。世界観案のプレイヤーレビューで、同型の「共鳴」が同じ理由で下位評価だった | **用語は、それが指す操作と字面で繋がっていること** |

### 根本原因

**1つの軸に複数の問いを兼任させていた。**

「種類」に以下すべてを答えさせようとしていた:

- どの棚に置くか
- 誰が買うか
- 何から作れるか
- 何と取り合わせるか
- いつ解禁されるか

この5つはアイテム空間を**別々の線で切る**ので、1分類で全部やると必ず破綻する。
矛盾にぶつかるたびに「軸が1本足りない」という信号が出ていた。

| tier | 品 |

| 2 | パン、ワイン、トマトソース、本 |

### 取得ルートは既に3種類ある（設計として成立している）

| ルート | 例 | 利幅 | コスト |

| ① 仕入れて売るだけ | りんご・ミルク・ボトル（レシピなし） | 約2倍 | 即座 |
| ② 素材を買って作る | パン・ワイン・ソース・本 | 2.5〜13.5倍 | 店を閉める |
| ③ 作ったものから作る | サンドイッチ | 12.5倍 | さらに手間 |

**足りないのはプレイヤーにこの3ルートが見えていないこと。**

## 6. 想定しているデータ構造（暫定）

> ⚠ **この節のコード例は失効した（2026-09-06）。**`要素`（平らなタグ袋）は面に分割され、
> `placeable` は廃止され、面の中身も Phase 2 で確定した（贅沢さ・向く土地）。
> **現行の確定形は [Phase 2 §4・§5](../application-design/cycle4-phase2-axes.md) を参照。**
> **「取り合わせを2層で書く理由」（この節の後半）は有効**（層1・層2の考え方は Phase 2 に引き継がれている）。

```ts
// アイテムが持つのは「事実」だけ
item = {
  主種類: '食品',              // 1つ・必須・不変。これは何であるか
  tier: 2,                     // レシピから自動導出（1 + max(材料のtier)）
  要素: ['生鮮', '子供向け'],   // 0〜N個。どんな性質を持っているか
  placeable: true,             // 棚に置けるか（素材は false）
  // shape, color, price ...
}

// 意味づけはすべて規則側。条件言語は共通
条件 = 主種類=='食品' | tier>=4 | 要素∋'贅沢'   （の任意の組み合わせ）

取り合わせ規則 : 条件 × 条件 → 売れやすさ / 値 / 集客
客の好み : 条件        → その客の購買率補正
入荷解禁 : 条件        → いつ店に並ぶか
```

### 取り合わせを2層で書く理由

現行は**アイテムID同士の直書き**（`apple: { adjacentItemId: 'milk' }`）。
100品に増えると組み合わせが数百行になり、**1品足すたびに既存全品との関係を見直すことになる**。
これが「拡張しづらい」の本丸。

```ts
// 層1: 条件規則（広く浅く・数十行で全品カバー）
{ when: ['食品', '飲料'],     type: 'sales_rate', mult: 1.15 }
{ when: ['贅沢', '贅沢'],     type: 'price_up',   mult: 1.20 }
{ when: ['生鮮', '生鮮'],     type: 'sales_rate', mult: 0.9  }  // 負の取り合わせも書ける

// 層2: 個別規則（狭く深く・名物コンビだけ手で作る）
パン × ワイン → price_up 1.3
```

→ 新しい品は要素を付けた瞬間に既存全品と正しい取り合わせになる。**追加コストが定数になる。**

## 7. 提案した設計アプローチ

各フェーズで**「決めないこと」を明示する**のが肝。数値を出すのが早すぎたのが失敗の大半だった。

### Phase 0 — 不変条件を書く
永久に満たすべき条件だけを、判定可能な形で。1ページ。

> **実施済み（2026-09-06）。**下の4本は当時の草案。確定版は INV-1〜6 ＋ 判定規律 PR-1〜3 で、
> → [cycle4-phase0-invariants.md](../requirements/cycle4-phase0-invariants.md) にある。

```
・アイテムを1つ足しても、既存アイテムの属性は変わらない
・1つの軸は1つの問いにしか答えない
・導出できる属性は手で書かない
・規則はアイテムを知らない（条件式だけを見る）
```

**ここで決めない**: 軸の数、分類の中身、数値

> この4本があれば「素材→中間品→製品」は1本目で、「書物」は2本目で落ちていた。

### Phase 1 — 問いを列挙して軸に割り当てる
アイテム体系が答えるべき問いを全部挙げ、各問いを**ちょうど1つの軸**に割り当てる。
ここで軸の本数が決まる（数えるだけなので議論不要）。

**ここで決めない**: 各軸の値

### Phase 2 — 各軸の定義を1行で書く
「tier とは加工の深さである」レベルの定義だけ。

**ここで決めない**: 語彙・数値

### Phase 3 — 最小実装で殴る
型定義 + 実アイテム20品 + 規則評価器を書いて動かす。**ここで初めて具体値を入れる。**

> 文書での議論は「案を出す→直感で判定」しか手がなく当たり判定が曖昧だった。
> コードなら「この分類だと箱が空になる」「この規則は書けない」が事実として出る。

### Phase 4 — 拡張ストレステスト
新しい品30個と新レシピ10本を投げ込み、Phase 0 の不変条件が破れるか確認。
破れたら **Phase 1 に戻る**（戻り先が決まっているので全部やり直しにならない）。

## 8. なぜ右往左往したか（プロセスの反省）

| 原因 | 内容 |
|---|---|
| **要件を決めずに解に飛んだ** | 「この体系が満たすべき条件」を書かないまま分類案を作ったので、新しい制約が出るたびに前提が変わった |
| **決定順を無視した** | tier の定義が決まれば主種類が背負うべきものは自動的に決まる。逆順にやったので後から前を壊した |
| **毎回"完成品"を出した** | 完成した設計は全体で否決される。次の1決定だけ出すべきだった |
| **実物なしで分類を評価した** | 中身が無い箱を設計していたので、空箱・過疎箱が事後にしか発覚しなかった |

ただし**円環ではなく螺旋**。反転のたびに軸が1本ずつ確定しており、
構造（§2）は固まっている。残っているのは各軸に入れる語彙（§4）だけ。
