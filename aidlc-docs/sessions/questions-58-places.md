## Q1. 強化へ行く場所の名前は「強化」か「改装」か

**[Answer]**: **B（改装）** ／ 回答者: PO ／ 2026-09-12
> 原文: 「BBでいいと思います。」

⚠ **main の推奨（A）は採られなかった。**「改装は棚しか指さない」という懸念は PO に提示済みで、
そのうえで B が選ばれた。**見出しもボタンも「改装」にする。**

### 何を決めるか

`店 ⇄ 商人のところ ／ 工房 ／ ???` の3つめの名前。**画面の見出しと右のボタンの文字**になる。

### なぜ今必要か

**場所の名前は、そこで何ができるかの唯一の説明になる。**
いまのダイアログは「強化」という見出しだけで、中に入るまで中身が分からなくてよかった。
場所にすると、**行く前に名前だけで選ぶ**ことになる。

### 選択肢

| | 名前 | 中身との一致 | 「場所」らしさ |
|---|---|---|---|
| **A（既定）** | **強化** | **4系統すべてを指す** | 低い（場所の名前ではない） |
| B | 改装 | **棚しか指さない**（来客・利益率・手際は改装ではない） | 高い |
| C | 別の名前（例: 商会・親方のところ） | — | — |

### 推奨と理由

**A を既定にして実装する。**
[bundle-f-places-plan.md](../construction/plans/bundle-f-places-plan.md) には「改装」と書いてあるが、
**中身は 棚・来客・利益率・手際 の4系統**（`Upgrades.UPGRADE_KINDS`）で、
**改装と呼べるのは「棚」だけ**である。来客や手際を改装と呼ぶと、
**名前が中身より狭くなり、来客の強化に行き着けない。**

### 影響

- **文字だけ。**`PlaceFrame` に渡す見出しと、右パネルのボタンのラベル1つ
- 回答が B・C でも**差し替えは1行**。構造は変わらない

### 参照

- `src/components/progress/Upgrades.ts`（`UPGRADE_KINDS = ['棚','来客','利益率','手際']`）
- #58 本文 ／ `bundle-f-places-plan.md` の「決定済みの前提と出典」

## Q2. セーブ／ロードも「場所」でよいか

**[Answer]**: **B（ダイアログのまま）** ／ 回答者: PO ／ 2026-09-12
> 原文: 「BBでいいと思います。」

→ **`SaveLoadMenu` は触らない。**場所は **商人のところ／工房／改装 の3つ**。
`GameScene` の「手が止まっているか」の判定は `placeFrame.isShown() || saveLoadMenu.isVisible()` の2項になる。

### 何を決めるか

セーブ／ロードを、他の3つと**同じ器**（中央が入れ替わる）に載せるか、
**ダイアログのまま**残すか。

### なぜ今必要か

**#58 の理由は「棚を覆うと判断の材料が隠れる」。**
セーブに棚を見ながらの判断は要らないので、**この理由はセーブには効かない。**
一方 #58 本文は「作り替えるUIが4つ（仕入れ・強化・クラフト・**セーブ**）」と数えている。

### 選択肢

| | | 結果 |
|---|---|---|
| **A（既定）** | **同じ器に載せる** | 画面の作りが1つで済む。ただし「記録しに行く」という場所ではない言い方になる |
| B | ダイアログのまま | 覆い方が2種類になる（場所とダイアログ）。`SaveLoadMenu` は触らない |

### 推奨と理由

**A。**#58 が4つと数えているのが直接の根拠。加えて、**覆い方を2種類持つと、
どちらで出すかの判断が以後ずっと付いて回る。**器が1つなら、その判断が要らない。

### 影響

- B なら `SaveLoadMenu` は今のまま（暗幕つきダイアログ）。**作業は減る**
- ただし `GameScene` の「場所にいるか」の判定に、**ダイアログの分岐が1本残る**

### 参照

- #58 本文「## 規模」／ `src/ui/SaveLoadMenu.ts`

## Q3. 品出しの型（マイセット）は3つでよいか

**[Answer]**:

⚠ **止めずに既定（3つ）で実装済み**（PO「いちいち止まるな」2026-09-12）。変えるなら定数1つ。

### 何を決めるか

覚えておける型の数（`ShelfPresets.PRESET_COUNT`）。

### なぜ今必要か

**島は4つ**なので、4つにすると「島ごとに1つ」と読める。
3つにすると**島とは別の使い分け**（「売る型」「作る型」）に開かれる。

### 選択肢

| | | 結果 |
|---|---|---|
| **A（実装済み）** | **3つ** | 島と1対1に見えない。**島ごとに1つと決めつけない** |
| B | 4つ | 島ごとに1つ、と読める。**自動切り替えを期待されやすい** |
| C | もっと多く（6など） | 画面が縦に伸びる（1枠120px。3枠で 360px） |

### 推奨と理由

**A。**⚠ **島に型を紐づけて自動で切り替えると、方針6「取捨選択を繰り返させる」と逆を向く。**
4つにすると、その期待を招く。

### 影響

定数1つ。**画面は枠の数だけ縦に伸びる**（領域の高さは 598px、一覧に使えるのは 456px なので **3枠まで**）。
⚠ **4つ以上にするなら1枠の高さを下げる必要がある。**

## Q4. 型はセーブしないと残らない。それでよいか

**[Answer]**:

⚠ **止めずに既定（セーブデータに入れる）で実装済み。**

### 何を決めるか

覚えた型の置き場。**セーブデータの中**か、**セーブとは別の場所**（ブラウザに常駐）か。

### なぜ今必要か

**セーブデータに入れると、覚えたあとセーブせずに閉じると型も消える。**
別の場所に置くと、**ロードしても型が残る**かわりに、**別のセーブの型が混ざる。**

### 選択肢

| | | 結果 |
|---|---|---|
| **A（実装済み）** | セーブデータの中 | 型は盤面の内容なので筋が通る。⚠ **セーブしないと残らない** |
| B | セーブとは別（ブラウザに常駐） | 閉じても残る。⚠ **別のセーブで覚えた型が出てくる**（品を持っていない型） |

### 推奨と理由

**A。**型は「その周回で手に入れた品の並べ方」なので、**セーブの中身と切り離せない。**
B は、まだ手に入れていない品の型が出てきて**空の棚が並ぶ。**

### 影響

`SaveData.shelfPresets`（省略可にしてあるので**古いセーブも読める**）。

## Q5. 手持ちが0の品も型どおりに並べてよいか

**[Answer]**:

⚠ **止めずに既定（並べる）で実装済み。**

### 何を決めるか

型を呼び出したとき、**いま持っていない品**をどうするか。

### なぜ今必要か

⚠ **棚は在庫を持たない**（段2.5）ので、**0個でも置ける。**置くこと自体は可能で、
置いた区画は**赤枠・「売り切れ」**として出る。

### 選択肢

| | | 結果 |
|---|---|---|
| **A（実装済み）** | **並べる**（売り切れとして赤く出る） | **何を仕入れ直すか**が盤面にそのまま出る |
| B | 飛ばす | 盤面が歯抜けになる。**何が抜けたのか分からない** |

### 推奨と理由

**A。**赤枠は**既にある仕組み**（`FloorRenderer.LOW_STOCK`）で、
「補充すべき場所が枠の色だけで分かる」ようにしてある。**型を呼ぶと買い物リストになる。**

### 影響

無し（置く／置かないの分岐1つ）。
